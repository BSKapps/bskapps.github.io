## Button Maker

### HIGH - export filenames mislabel numbered buttons
**File:** `buttonmaker/js/series.js:111` (`firstText()`) and `:126-128` (`variantFileName()`)

`variantFileName()` names an export from `v.companionText`, which is set via `firstText(d)` - the value of the *first* text layer with a non-empty value, not the layer that actually varies. The built-in "INPUT 1-8" preset (`buttonmaker/js/presets.js` ~486-505) sets `texts[0].value = 'INPUT'` (static) and pushes the numbered `{label}` token as a *second* layer. Result: `companionText` is `'INPUT'` for all 8 variants.

Impact:
- `exportPng()` (`export.js:140-147`) always downloads `input.png` regardless of which of INPUT 1-8 is selected.
- `exportZip()`/`exportReaper()` (`export.js:67-125`) only avoid outright collisions via `uniqueName()`'s positional incrementing counter (`input.png`, `input-2.png`...), which silently desyncs from the visible number the moment items are reordered or one is deleted.
- Any custom design using the same "static label first, numeric token second" text-layer order hits the same bug.
- Note: `copyPng()` is NOT affected (it copies to clipboard, doesn't touch a filename) - verifier caught this overstatement in the original finding.

Fix direction: `firstText()` (or `variantFileName`) needs to prefer the text layer that actually contains the substituted token/varies per item, not simply the first non-empty one.

### MEDIUM - partial-edge border ignores corner radius/squircle
**File:** `buttonmaker/js/renderer.js:330-353`

The `allEdges` branches (336-343) correctly stroke the border along the squircle/rounded path. The final `else` branch (344-351, used whenever at least one of the T/B/L/R edge checkboxes is off) draws raw full-length straight lines (`moveTo(0,o)/lineTo(size,o)` etc.) with zero awareness of `design.shape.radius`/`design.shape.squircle`. The shape clip is already torn down by `ctx.restore()` (327-328) before this runs, so on a rounded/squircle button with a partial-edge border, the border line visibly overshoots past the curved corner into transparent canvas - in the real exported PNG, not just the editor preview. Both controls (edge checkboxes, radius/squircle) sit in the same always-open Border/Shape section (`index.html` 83-93), so this is directly reachable, not a hypothetical.

Fix direction: the partial-edge branch needs the same squircle/rounded-aware path construction as the `allEdges` branches, clipped/inset consistently.

### MEDIUM - preset import with no `name` field permanently breaks Save/Rename
**File:** `buttonmaker/js/presets.js:621` (`applyImportedFile()` validity filter)

The import filter only requires `p.design`/`p.design.bg`/`(p.design.texts || p.design.text)` - never checks `p.name`. A hand-edited or third-party JSON missing `name` on one entry is accepted into `localStorage` via `saveUserPresets()`. That entry then renders as a group literally titled `"undefined"` (`presets.js:789`, `undefined` coerced to string). Worse: both the Save handler (`presets.js:582`) and the Rename handler (`presets.js:802`) call `p.name.toLowerCase()` over the *entire* preset list with no guard, so importing one bad entry throws an uncaught `TypeError` and silently kills Save-to-My-Presets and Rename for every preset from then on, until the user notices the "undefined" group and manually deletes it (delete still works, doesn't touch `.name`).

Fix direction: validate/require `name` (or backfill a default) in `applyImportedFile()`'s filter before accepting an entry.

### LOW - Numbers From/To fields skip `emit()`
**File:** `buttonmaker/js/ui.js:585-594` (`bindSeriesNum`)

Unlike `bindRange`/`bindColor`/`bindSelect`/`bindSeg` (all call `emit()` at the end), `bindSeriesNum` mutates `state.series[key]` directly and never calls `emit()`. Downstream effect: the debounced `pushHistory`/`saveSession` (undo + localStorage persistence) and the live `{n}`-token canvas substitution go stale until some other control fires `emit()`. Verifier downgraded this from medium to low: the primary documented workflow ("Make a numbered set" button) is unaffected since that handler re-dispatches `change` and calls `emit()` itself; the `{n}` token path is undocumented/power-user-only; and the staleness self-heals on the next control touch. Only a reload timed exactly between editing just this field and any other interaction would lose the edit.

Fix direction: add `emit()` at the end of `bindSeriesNum`'s change handler, matching the other four binders.

### LOW - `.help-toggle` styled with undefined CSS variable
**File:** `buttonmaker/css/style.css:948-963`

`.help-toggle` sets `color: var(--text-muted)` and hover `border-color: var(--text-muted)`. This stylesheet's `:root` (lines 1-21) defines `--muted: #A9A9AF`, never `--text-muted` (that token is real in the *main site's* `css/site.css`, not this self-contained one - looks like a copy-paste artifact). Because `color` is inherited, the invalid `var()` falls back to the inherited ancestor value (bright, not muted), so the "?" hint toggle on the Download card never renders dim in its default/inactive state, undercutting the on/off contrast against its blue "active" state.

Fix direction: change both `var(--text-muted)` references to `var(--muted)`.

## Website

### Admin panel (`admin/index.html`) - biggest cluster, review this file first

#### HIGH - saving one tab clears the wrong tab's unsaved-changes indicator
**Lines:** `save()` 950-956, `saveContent()` 958-990, `saveArticle()` 992-1026 (specifically the unconditional `tbBtn.classList.remove('active')` at 981 and 1017)

`save()` dispatches to `saveArticle()` OR `saveContent()`, never both. If you edit a Content field (`dirty=true`), switch to the Articles tab without saving, edit an article (`articleDirty=true`), then click Save: `saveArticle()` runs alone, clears `articleDirty`, and unconditionally strips the `.active` class that makes the Save & Publish button clickable (CSS: `opacity:0.35; pointer-events:none` when inactive) - even though the Content-tab edit is still unsaved in memory. Same bug in reverse via `saveContent()`. Net effect: the save button looks and behaves like "nothing to save" while a real edit sits unsaved; navigating away or closing the tab loses it silently.

Fix direction: both `saveContent()` and `saveArticle()` should call the existing `refreshSaveBar()` (943-948, checks `dirty || articleDirty`) instead of unconditionally removing `.active`.

#### HIGH - content.json load path corrupts non-ASCII text (encode/decode asymmetry)
**Line:** `init()` at 773 - `data = JSON.parse(atob(file.content.replace(/\n/g, '')));`

This is the *only* decode path in the file that doesn't UTF-8-recombine. Compare `saveContent()` (967): `btoa(unescape(encodeURIComponent(...)))` (correct) and `loadArticle()` (1085): `decodeURIComponent(escape(atob(...)))` (correct). Since `atob()` alone only reassembles a Latin-1 "binary string," any multi-byte UTF-8 character typed into a content field (curly quote, accented letter, (R)/(TM)) comes out as mojibake on next load of `/admin`, and the next unrelated save re-serializes the *entire* `data` object, permanently baking the corruption into the live, git-committed `_data/content.json` - the public site's source of truth for names/taglines/descriptions/features. Currently dormant: `_data/content.json` today contains no non-ASCII bytes (checked at audit time), so nothing is broken yet, but the bug is real and will trigger the moment someone pastes a curly quote into the admin.

Fix direction: change line 773 to `JSON.parse(decodeURIComponent(escape(atob(file.content.replace(/\n/g, '')))))`, matching `loadArticle()`'s pattern.

#### MEDIUM - `init()` has no error handling for an expired/invalid token
**Lines:** 765-780

`init()` unconditionally hides `#login` and shows `#dashboard` (767-768) *before* the fetch resolves, then does `file.sha` / `atob(file.content...)` with zero `try/catch` and no `res.ok` check on the `ghFetch` response. Fine-grained GitHub PATs have a mandatory expiry; an expired/revoked token or a 401/403 makes `res.json()` resolve to an error body lacking `.sha`/`.content`, throwing an uncaught `TypeError` mid-init. `renderForm()`/`restoreTab()`/`loadApiKeys()` never run, so `#content-form` stays empty with zero visible error message - only recourse is noticing the static "Sign out" link.

Fix direction: wrap the fetch + parse in `try/catch`, check `res.ok`, and show a real error/re-login prompt on failure instead of a silently blank dashboard.

#### MEDIUM - save-bar auto-hide timer race
**Lines:** `saveContent()` 983, `saveArticle()` 1019 (identical `setTimeout(..., 3000)` pattern, no `clearTimeout` anywhere in the file)

After a successful save, a 3-second timer unconditionally strips the `.show` class from `#save-bar` regardless of current dirty state. If you edit another field within that window, `markDirty()`/`markArticleDirty()` correctly re-show the bar via `refreshSaveBar()` - but the earlier timer still fires at the 3s mark and hides it again, even though there are now unsaved changes. The smaller topbar button still reflects true state; only the more prominent bottom bar misleads.

Fix direction: store the timeout id and `clearTimeout` it on any subsequent `markDirty()`/`markArticleDirty()` call, or have the timeout check `dirty || articleDirty` before removing `.show`.

#### MEDIUM - libsodium loaded from CDN with no integrity check
**Lines:** 8-11 - `import sodium from 'https://cdn.jsdelivr.net/npm/libsodium-wrappers@0.7.15/+esm';`

No Subresource Integrity hash (native ES module imports can't carry one), loaded unconditionally on every page load, in the same page/origin that stores the GitHub PAT in `localStorage` (`bsk_token`, used elsewhere in the file, live dependency for `crypto_box_seal` when encrypting API keys at ~1393-1396 - not dead code). If jsdelivr, the npm package, or the network path were ever compromised, injected code would run with full page privileges and could read/exfiltrate the token (Contents + Secrets write access to both repos). This is a distinct, more specific risk layered on top of the already-accepted "token in localStorage for a single admin" tradeoff - not covered by that acceptance.

Fix direction: vendor libsodium locally (matching how `buttonmaker/vendor/jszip.min.js` is already handled in this same repo) instead of a live CDN import, removing the supply-chain surface entirely.

### Templates (Jekyll)

#### MEDIUM - guide layout footer is missing the Refund Policy link
**File:** `_layouts/guide.html:71`

CLAUDE.md documents the footer as identical on every page: "Contact - About - Privacy - Terms - Refund Policy." Every other page type has all five links; `_layouts/guide.html`'s footer only has four (no `/refund`). This layout renders 4 live guide pages (fetch-puppy-guide, lab-assistant-guide, target-trace-guide, stimulus-guide), and the same missing link is separately hand-copied into all 25 individual `articles/*/index.html` pages too - confirmed via `grep -L "Refund Policy" articles/*/index.html`. A reader on a paid product's official guide page (reached from the product page's "Full guide" link) has no footer path to the refund policy.

Fix direction: add the `/refund` link to `_layouts/guide.html`'s footer to match every other page; separately decide whether to backfill the 25 article pages (each has the footer hand-copied rather than templated).

#### LOW - guide layout's `og:image` is a square icon, missing width/height
**File:** `_layouts/guide.html:11-15`

No `og:image:width`/`og:image:height` tags at all, unlike every product page. The 4 guide JSON files (`_data/guides/*.json`) point `web.ogImage` at a 512x512 or 1024x1024 square app icon rather than the proper 1200x630 `og-*.png` cards that already exist in `images/` for these same products (e.g. `og-stimulus.png`) but aren't referenced. Social platforms will guess the aspect ratio or crop badly when a guide page is shared.

Fix direction: point `web.ogImage` in each guide JSON at the matching `images/og-*.png`, and add the width/height meta tags to `_layouts/guide.html` to match the product-page pattern.

### Accessibility

#### MEDIUM - lightbox prev/next buttons have no accessible name, on all 5 product pages
**Files:** `quickerip/index.html:177-178`, `labassistant/index.html:183-184`, `fetchpuppy/index.html:145-146`, `targettrace/index.html:148-149`, `stimulus/index.html:143-144`

`<button class="lightbox-arrow prev" id="lb-prev">&#8249;</button>` (and the `next`/`&#8250;` twin) have no `aria-label`, `title`, or hidden text, and no JS ever sets one. `css/site.css` has no `.sr-only`/`.visually-hidden` class to compensate. A screen reader announces "button" plus a stray punctuation glyph, no indication these navigate prev/next screenshot. Reachable whenever the lightbox is open (`.lightbox.active ~ .lightbox-arrow { display: flex; }`).

Fix direction: add `aria-label="Previous screenshot"` / `aria-label="Next screenshot"` to both buttons on all 5 pages (identical markup, one fix pattern to replicate 5x).

## Suggested fix order

1. Admin panel HIGH x2 (cross-tab save data-loss, content.json UTF-8 corruption) - both are silent-corruption/data-loss bugs on the CMS that edits the live site's source of truth.
2. Button Maker HIGH (export filename mislabeling) - user-facing, affects a shipped built-in preset.
3. Admin MEDIUM x3, Button Maker MEDIUM x2, templates MEDIUM x1, accessibility MEDIUM x1.
4. Everything LOW, and the dead-CSS cleanup (mechanical, low risk, do last / batch together).

Per this repo's own rules (CLAUDE.md): surgical fixes only, no unrelated refactors, cross-review the diff before commit, bump Button Maker's `?v=` on every touched file (and every other file that imports it - grep `\?v=[0-9]+` afterward to confirm none were missed).
