How macOS routes traffic across multiple adapters

25 April 2026 · Updated 3 October 2026

macOS sends each packet out the adapter with the most specific matching route. Anything else goes to the default route, which belongs to the highest adapter in Set Service Order that has a router. netstat -rn -f inet shows the table.

Every IP packet your Mac sends has to go out a specific physical adapter. With one adapter, the choice is obvious. With two or three, macOS has to decide - and its decision process is not always obvious to the person who set up the interfaces.

This is Part 2 of a companion pair. Part 1 covers the practical setup: service order, addressing, and preset switching. This article explains the underlying routing mechanics and why certain configurations break.

The routing table

macOS maintains a routing table: a list of rules that map destination IP ranges to outgoing interfaces. Every packet gets checked against this table before it leaves the machine, and the most specific rule that matches wins.

You can read the table at any time:

netstat -rn -f inet

An example, trimmed, from a Mac with Wi-Fi on en0 and one wired adapter on en7 (your addresses, link numbers and adapter names will differ):

Routing tables

Internet:
Destination        Gateway            Flags               Netif Expire
default            192.168.1.1        UGScg                 en0
127                127.0.0.1          UCS                   lo0
127.0.0.1          127.0.0.1          UH                    lo0
169.254            link#15            UCS                   en0      !
192.168.1          link#15            UCS                   en0      !
192.168.1.10/32    link#15            UCS                   en0      !
192.168.10         link#21            UCS                   en7      !
192.168.10.5/32    link#21            UCS                   en7      !

Each row is a rule. Destination is the target range. Gateway is either a router IP (for routes that need a next hop) or link#N (meaning: send directly on that interface, no router needed). Netif is the physical adapter. Ignore the Expire column for this.

Two types of entries matter here:

  • Connected routes - added automatically when you assign an IP to an interface. If en0 is 192.168.1.10 with a /24 mask, macOS immediately adds a route saying "anything in 192.168.1.0/24, send directly on en0". No gateway involved. The host is assumed to be reachable on the wire.
  • The default route - the catch-all. The row labelled default (or destination 0.0.0.0) covers everything that does not match a more specific rule. All internet traffic, all traffic to unknown subnets, goes this way. This is the route people usually mean when they talk about a "default gateway".

How the default route gets assigned

macOS keeps one primary default route per address family (IPv4 and IPv6 have separate tables, but the logic is the same). When more than one adapter has a gateway configured, it has to pick which one gets it.

The deciding factor is service order - the ranked list under System Settings, Network, three-dots menu, Set Service Order. The highest-ranked adapter that is currently up and has a gateway configured gets the primary default route. Adapters with no gateway never compete for it; they are reached through their own subnet routes wherever they sit in the list. The exception is the 169.254 link-local range: macOS keeps a single 169.254 route on the primary adapter (en0 in the table above), so a browser, Companion or QLab reaching a 169.254 device can send that traffic out Wi-Fi. Dante Controller is fine because you pick its interface. For anything else, turn Wi-Fi off or put the devices on a DHCP or static subnet.

The other adapters with a gateway may keep a default route of their own, scoped to that adapter. It shows as a second default line with an I in the flags (RTF_IFSCOPE in man netstat), and only traffic tied to that adapter uses it:

default            192.168.1.1        UGScg                 en0
default            192.168.10.1       UGScIg                en7

This is why service order matters in production systems. If Wi-Fi is above your Ethernet adapter and both have a gateway, all your internet traffic and any "unknown destination" traffic goes out Wi-Fi, even if you physically plugged into a fast wired network. The wired adapter is active and works fine for its own subnet, but it will never carry the default-route traffic until you move it above Wi-Fi in the list.

You can check which adapter currently holds the default route with:

netstat -rn -f inet | grep default

The line without an I is the primary. Or look at the Quicker IP menu - it marks the adapter currently carrying the default route with a blue status dot.

Why the same subnet on two adapters breaks things

When you assign an IP to an interface, macOS adds a connected route for that entire subnet on that interface. If Wi-Fi is on 192.168.1.50 with a /24 mask, the routing table gets an entry: "192.168.1.0/24 goes via en0". If you then plug in an Ethernet adapter and also put it on 192.168.1.x - say, 192.168.1.100 with a /24 mask - macOS needs a second entry: "192.168.1.0/24 goes via en7".

Now there are two rules for the same destination range. macOS picks one as the primary route for that subnet and may keep the other only as an interface-scoped route (flag I) for traffic already tied to that adapter. The outcome:

  • Traffic to any device on 192.168.1.x goes out whichever adapter holds the primary route, regardless of which adapter is physically on the same wire as the device you are trying to reach.
  • If a Dante device is at 192.168.1.20 and it is plugged into the same switch as your Ethernet adapter, but Wi-Fi holds the 192.168.1.0/24 route, traffic from the Mac to that device can leave on Wi-Fi. The Dante device never sees it. The device is physically there, correctly configured, and Dante Controller reports it as offline.
  • The same applies to any unicast traffic: ARP requests, pings, OSC, everything. The kernel does not know that 192.168.1.20 is only reachable via en7. It just follows the route.

The reason this produces "mixed results" rather than a clean failure is that the winner can change. When either adapter drops and reconnects, the route can move to the other one. Some traffic gets through before the change, some after. You get intermittent failures that look random but come from two adapters competing for the same subnet.

The gateway makes it worse

The connected-route problem above applies whenever two adapters share a subnet - even if neither has a gateway. But the situation gets worse when both adapters have a gateway configured.

With two gateways on the same subnet, the two adapters compete for both the subnet route and the default route, so internet traffic and show traffic can end up on different adapters, and that can change when either link drops.

Which is why the rule holds: if an interface doesn't need a gateway, don't give it one. An audio network, a show control LAN without internet access, a static-IP Dante subnet - none of these need a router field. Leave it empty. That keeps the default route unambiguous and removes one source of conflict.

How Quicker IP detects this

Quicker IP checks every pair of connected adapters for subnet overlap, leaving out self-assigned 169.254 addresses. It distinguishes two scenarios:

  • Shared subnet, no gateway conflict - two adapters on the same subnet, but only one (or neither) has a gateway configured. Traffic to that subnet can still leave on the wrong adapter, but the default route is unambiguous. Quicker IP shows this in grey as "Shared with en7, no conflict", naming the other adapter.
  • Gateway conflict - two adapters on the same subnet and both have a gateway configured. This is the full problem: both the subnet route and the default route are contested. Quicker IP shows this in red as "Overlaps en7", naming the other adapter, and sends a Gateway Conflict notification the first time it sees the conflict, giving the CIDR of the clashing subnet.

The warning appears on the Subnet line in each affected adapter's Network Info. A static adapter that is unplugged shows a greyed "Would overlap" note when its configured subnet matches a live one, so you see the clash before the cable goes in. Quicker IP reads the configuration; it doesn't watch traffic. A grey warning still means traffic to that subnet can leave on the wrong adapter. A red one means both routes are contested. Fix either before the show.

What to do when you see an overlap

  • Turn one adapter off. If you don't need both active at the same time, this is the cleanest fix. Wi-Fi off during a show is the standard answer for Dante systems.
  • Put them on different subnets. Change one of the conflicting networks to a range that doesn't collide. 192.168.10.x, 172.16.x.x, 10.x.x.x - anything that doesn't overlap with the other interface. This is the right fix when you need both adapters active simultaneously.
  • Remove the gateway from the adapter that doesn't need it. If one of the two is a closed network (no internet), clear the router field. This eliminates the gateway conflict and reduces the connected-route problem to a grey warning rather than a red one.

The underlying cause is almost always that someone assigned static IPs without checking whether the subnet range they chose was already in use elsewhere on the same machine. A fresh venue Wi-Fi on 192.168.1.x is probably the most common trigger.
