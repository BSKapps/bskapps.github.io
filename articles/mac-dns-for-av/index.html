DNS on a Mac: how it works and how to set it per adapter

5 July 2026 · Updated 3 October 2026

DNS is set per adapter in System Settings > Network > the adapter > Details > DNS, but macOS answers most lookups from the primary service's resolvers. Put DNS on the internet adapter only and leave show LANs empty.

On a single-adapter Mac you never think about it. On a show Mac running Wi-Fi plus a control LAN plus an audio network, DNS is one of the classic ways to break internet access without touching the internet connection.

Where DNS settings actually live

Each network interface carries its own DNS server list, filled one of two ways:

  • From DHCP - the router hands out DNS servers along with the address. This is the default and what you're using on Wi-Fi and home networks.
  • Manually - servers typed into the interface's DNS tab, which then override anything DHCP offered on that interface.

The catch on a multi-adapter Mac: macOS builds one resolver configuration from all of those lists. Most lookups go to the servers of the primary service - the highest adapter in Set Service Order that has a router. Every adapter's servers are also kept as scoped resolvers, used only by lookups tied to that adapter. So if a show LAN adapter has a router and DNS servers filled in and sits above Wi-Fi, it becomes primary, and web lookups go to servers that can't reach the internet. They stall and time out, and browsing looks dead while the Wi-Fi is connected and perfectly healthy. This is one of the two classic multi-adapter traps (the other is duplicate gateways, covered in Static IPs and multiple network adapters on a Mac).

The rule: DNS only where the internet is

Simple and worth making a habit:

  • Internet-facing interface (usually Wi-Fi): gets DNS, usually via DHCP. Leave it alone.
  • Show control LAN: no router and no DNS servers. Consoles and media servers are reached by IP address; there's nothing for DNS to resolve there.
  • Audio network (Dante and friends): nothing. Dante devices default to DHCP and fall back to link-local addresses when no DHCP server answers. Either way, no router and no DNS typed in on the Mac.

An empty DNS list on an isolated network is correct. A filled-in one points at nothing.

How to set DNS per adapter

In System Settings:

  1. Choose Apple menu > System Settings, then click Network.
  2. Click the adapter, then click Details.
  3. Click DNS.
  4. Click the Add button under DNS Servers and type an address, or select a server and click Remove. Click OK.

For a show LAN, remove every server from its list. For the internet adapter, leave the DHCP servers alone unless you have a reason below.

The same from Terminal. List the service names first, then set or clear servers on one service:

networksetup -listallnetworkservices
networksetup -getdnsservers "Wi-Fi"
networksetup -setdnsservers "Wi-Fi" 1.1.1.1 1.0.0.1
networksetup -setdnsservers "Show LAN" empty

-getdnsservers shows what's set on that service, and empty in place of addresses clears the list. Changing settings needs an admin account; if the command refuses, run it again with sudo in front.

See which DNS servers the Mac is using

scutil --dns

This only reads. The first section, DNS configuration, is what answers most lookups: resolver #1 lists its nameservers, and its if_index line names the adapter they belong to. If that adapter isn't your internet adapter, you've found the problem. The section headed DNS configuration (for scoped queries) lists each adapter's own servers.

When to set DNS manually

  • Venue networks with broken or filtered DNS. The connection works but lookups fail or redirect. Setting a public resolver - 1.1.1.1 (Cloudflare) or 8.8.8.8 (Google) - on that interface routes around the venue's servers.
  • Captive portals, briefly. Note the reverse case: some venue login pages only resolve through the venue's own DNS, so if the portal won't load, go back to automatic until you're through it.
  • Static-IP setups. A manually addressed interface gets no DHCP extras, so if that interface is also your internet path, DNS has to be typed in alongside the address.

.local names are not DNS

Names like console.local resolve through Bonjour (mDNS) - multicast on the local subnet, no DNS server involved. That's why a QLab machine can find gear by name on a network with no DNS at all, and why those names stop resolving across subnets: multicast doesn't cross routers by default. If .local names work but real hostnames don't, DNS is your problem; if it's the other way around, look at multicast and subnetting, not DNS.

When lookups go stale

macOS caches DNS answers, and after network changes the cache can hold stale entries - the machine keeps resolving a name to an address that's no longer right. The standard reset:

  • sudo dscacheutil -flushcache; sudo killall -HUP mDNSResponder

Safe, and the first thing to try when one machine resolves a name wrongly while others are fine.
