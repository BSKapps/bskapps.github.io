DNS on a Mac: how it works and how to set it per adapter

5 July 2026

DNS is the part of networking everyone treats as magic right up until the internet "stops working" on a machine that is, in fact, connected fine. On a single-adapter Mac it mostly is magic. On a show Mac running Wi-Fi plus a control LAN plus an audio network, DNS is one of the classic ways to break internet access without touching the internet connection - because DNS settings live per interface, but lookups are answered system-wide.

Where DNS settings actually live

Each network interface carries its own DNS server list, filled one of two ways:

  • From DHCP - the router hands out DNS servers along with the address. This is the default and what you're using on Wi-Fi and home networks.
  • Manually - servers typed into the interface's DNS tab, which then override anything DHCP offered on that interface.

The catch on a multi-adapter Mac: macOS builds one system-wide resolver configuration from all of those per-interface lists, and the service order decides whose DNS wins for general lookups. If your show LAN adapter sits above Wi-Fi in the service order and carries DNS servers that can't reach the internet, every web lookup on the machine dies - while the Wi-Fi is connected and perfectly healthy. This is one of the two classic multi-adapter traps (the other is duplicate gateways, covered in Running multiple network adapters on a Mac).

The rule: DNS only where the internet is

Simple and worth making a habit:

  • Internet-facing interface (usually Wi-Fi): gets DNS, usually via DHCP. Leave it alone.
  • Show control LAN: no DNS servers at all. Consoles and media servers are reached by IP address; there's nothing for DNS to resolve there.
  • Audio network (Dante and friends): nothing. Link-local addressing, no router, no DNS.

An empty DNS list on an isolated network isn't a missing setting - it's the correct setting. A filled-in one is a lookup path to a dead end.

When to set DNS manually

  • Venue networks with broken or filtered DNS. The connection works but lookups fail or redirect. Setting a public resolver - 1.1.1.1 (Cloudflare) or 8.8.8.8 (Google) - on that interface routes around the venue's servers.
  • Captive portals, briefly. Note the reverse case: some venue login pages only resolve through the venue's own DNS, so if the portal won't load, go back to automatic until you're through it.
  • Static-IP setups. A manually addressed interface gets no DHCP extras, so if that interface is also your internet path, DNS has to be typed in alongside the address.

.local names are not DNS

Names like console.local resolve through Bonjour (mDNS) - multicast on the local subnet, no DNS server involved. That's why a QLab machine can find gear by name on a network with no DNS at all, and why those names stop resolving across subnets: multicast doesn't cross routers by default. If .local names work but real hostnames don't, DNS is your problem; if it's the other way around, look at multicast and subnetting, not DNS.

When lookups go stale

macOS caches DNS answers, and after network changes the cache can hold stale entries - the machine keeps resolving a name to an address that's no longer right. The standard reset:

  • sudo dscacheutil -flushcache; sudo killall -HUP mDNSResponder

Cheap, safe, and the first thing to try when one machine resolves a name wrongly while others are fine.
