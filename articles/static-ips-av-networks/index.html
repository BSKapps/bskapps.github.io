Static IPs and multiple network adapters on a Mac for AV

18 April 2026 · Updated 3 October 2026

Give each adapter its own subnet. Only the internet adapter gets a router and DNS, and it goes at the top of the service order. Show LANs get an address and a subnet mask, nothing else.

A MacBook used in live production rarely has one network connection. Touring systems, installs, and even small corporate shows often have the same Mac on Wi-Fi, a wired control LAN, and a dedicated audio network at the same time. Each wants its own settings. macOS will happily run all three concurrently, but it will also happily route traffic out the wrong interface if you don't set it up.

The routing mechanics behind these rules are in Part 2 - how macOS routes traffic across multiple adapters.

Why you end up with multiple adapters

Typical setups that push you past a single interface:

  • Wi-Fi for internet access, remote support, and software updates.
  • One wired Ethernet adapter for a show control LAN: consoles, media servers, lighting, OSC traffic.
  • A second wired adapter, often on a Thunderbolt dock or second USB-C port, for the audio network (Dante, AVB, NDI).

Three networks on three subnets, none talking to each other.

Pick the right addressing per network

  • DHCP - router hands out an address. Default for Wi-Fi, home, office, most venue back-of-house. Leave it alone.
  • DHCP reservation - the router is configured to always hand your Mac the same address. Set on the router, not the Mac. Useful when something needs a stable address on a Wi-Fi network.
  • DHCP with manual address - macOS's "Using DHCP with manual address": you type the address, DHCP supplies the subnet mask and router. Quicker IP Pro calls this DHCP Reserved. Useful when you need a fixed address on a DHCP network and can't touch the router.
  • Static IP - Mac is set manually. The only option when the network has no DHCP server, or when the vendor has assigned you an address.
  • Link-local (169.254.x.x) - no DHCP server answers, so the Mac auto-assigns itself an unused address in 169.254.0.0/16. Set Configure IPv4 to "Using DHCP" and leave it. If there's nothing to respond, macOS falls through to link-local on its own after a short delay. This is how many Dante networks run day to day: Dante devices default to DHCP, fall back to link-local when no server answers, and discovery still works with nobody configuring anything. Don't dismiss it just because it feels like a fallback.

Service order: internet adapter on top

System Settings, Network, three-dots menu, Set Service Order. Service order decides which adapter that has a router carries the default route, and whose DNS answers most lookups. Adapters with no router - a show control LAN, a Dante network - are reached through their own subnet routes, whatever the order.

So put the adapter you want internet through at the top. On a prep day that's usually Wi-Fi, for software updates, cloud storage, or remote support while also on a show LAN. At a venue where the internet arrives on a wired port, it's that port. Show LANs need no router and no DNS, so where they sit doesn't change how show traffic reaches them. Putting the audio adapter on top, as Audinate suggests for Dante, does no harm as long as it has no router.

The exception is link-local: macOS keeps a single 169.254 route, on the primary adapter, so a browser, Companion or QLab reaching a 169.254 device can send that traffic out Wi-Fi. Dante Controller is fine because you pick its interface. For anything else, turn Wi-Fi off or put the devices on a DHCP or static subnet.

The real trap is two active adapters on the same subnet. macOS picks one route for that subnet and may keep the other only as a route tied to its own adapter, so traffic can leave on the wrong one. Reordering won't fix that; a different subnet will.

When the internet adapter changes from day to day, reordering by hand gets old. Locations fix that. A "Show" Location and a "Prep" Location, each with its own adapter settings and service order, and you swap between them instead of dragging rows in System Settings under pressure. Give each adapter only what it needs

Each interface has its own IPv4, DNS, and router settings. A common mistake is filling in all of them on every interface, which then fights with itself.

  • The internet-facing interface gets IP, subnet, router, and DNS. Usually all via DHCP.
  • A control LAN that has no internet access gets IP and subnet only. No router. No DNS.
  • An audio network on link-local gets nothing at all. Leave Configure IPv4 on "Using DHCP" and let macOS fall through to a 169.254.x.x address automatically. No router, no DNS.

If an interface doesn't need a gateway, don't give it one. With two gateways, which one carries the default route comes down to service order, and on the same subnet they fight over that subnet's route too. You'll spend an hour on it at the worst possible time. Quicker IP warns you: when two active adapters share a subnet and both have a gateway, Network Info shows a red "Overlaps" warning naming the other adapter and a Gateway Conflict notification names the subnet. When only one or neither has a gateway it shows a grey "Shared with en8, no conflict" - the default route is safe, but traffic to that subnet can still leave on the wrong adapter.

Two subnets on one port

Some systems put two subnets on one switch - a Yamaha console's Mixer Control and Device Control, for example, which Yamaha requires on different subnets. macOS can do this with a second network service on the same Ethernet port, given its own address. Quicker IP Pro's Add Address does it from the adapter's flyout: the second address becomes its own service, ordered below the first, with no gateway.

Switching between systems

All of this is fine when the Mac lives in the one system. The moment it travels - same laptop, different venue, different networks - each of those interfaces needs a different configuration. macOS makes that slow. System Settings, Network, interface, Details, TCP/IP, set Configure IPv4 to Manually, type the address, subnet mask and router, switch to DNS, add servers, click OK, back out. It is a lot of clicks, every venue.

macOS has a built-in feature called Locations (System Settings, Network, three-dots menu, Locations) that saves every service's settings and the service order, and lets you swap between them. It works. Building one per venue and keeping it current is the slow part.
