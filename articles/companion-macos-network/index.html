Companion on macOS: network setup and stability

25 April 2026

Bitfocus Companion runs as a local server on your Mac. It opens connections out to devices on the network -- consoles, media servers, QLab, lighting desks -- and listens for incoming connections from Stream Decks and remote surfaces. When it works, it's seamless. When it doesn't, the failure mode is usually not Companion itself but the Mac's network configuration underneath it.

Most of the traps here are the same ones covered in the multi-adapter networking articles: setup and service order, and how the routing table decides which adapter to use. This article applies those principles specifically to Companion.

How Companion uses the network

Companion has two sides to its networking:

  • Outbound connections -- Companion connects to devices using whatever protocol the module requires: TCP, UDP, OSC, HTTP, Telnet, or a device's proprietary protocol. Each of those connections goes out through an interface, chosen by the routing table based on the destination address.
  • Inbound connections -- Companion's web UI and API listen on port 8888. Stream Decks connected via USB talk to Companion directly. Remote surfaces (Stream Decks on other machines, phone-based surfaces) connect back to Companion over the network on a separate port.

The web UI and API bind to all interfaces by default, so you can reach them at localhost:8888 or at any of the machine's IP addresses. That part mostly just works. The outbound side is where routing causes trouble.

The routing problem in practice

Say you have a show control LAN on 192.168.10.x and Wi-Fi on 192.168.1.x. You have a lighting console at 192.168.10.50 and a media server at 192.168.10.80. Companion's modules for those devices have their IPs configured correctly. But if the routing table sends traffic to 192.168.10.x out the wrong adapter -- or the 192.168.10.x route doesn't exist because that adapter isn't connected yet when Companion starts -- those modules will sit in a disconnected state.

The most common version of this: Companion launches at startup while the wired adapter is still initialising. The routing table builds without the show LAN route, Companion tries to connect, fails, and marks the modules as offline. They may reconnect automatically once the adapter comes up, or they may not, depending on the module's reconnect behaviour. Restarting Companion after the network is fully up clears it every time -- but that's not a great habit to depend on.

The fix is making sure the wired adapter is up before Companion launches, and that service order puts it in the right position. If the show LAN is on a dedicated wired interface with no gateway, traffic to 192.168.10.x goes out that interface directly via the connected route. No routing ambiguity, no service order fight.

The same-subnet trap

This one catches people who set up a dedicated Ethernet adapter for the show LAN but happen to land on the same subnet as their Wi-Fi -- usually both end up on 192.168.1.x because that's the default for most consumer gear.

With two adapters on the same subnet, the routing table has two competing entries for 192.168.1.0/24. The kernel picks one. Companion's traffic to a device at, say, 192.168.1.50 goes out whichever adapter won -- which may not be the one physically connected to the device. The module shows as offline even though the device is right there. Flipping the service order or disconnecting Wi-Fi usually makes it start working, which confirms the diagnosis.

The reliable fix is different subnets on different adapters. If you can't change the show LAN, turn Wi-Fi off. Quicker IP Pro shows a red warning when two active adapters share a subnet and both have a gateway -- useful for catching this before Companion starts throwing connection errors.

Service order for a Companion rig

A typical setup has Companion on the same Mac as QLab, with Wi-Fi for general use and one or two wired adapters for the show. A workable service order for show day:

  • Show control LAN (wired) -- first, so traffic to devices on that subnet goes out the right adapter
  • Audio network (wired, if applicable) -- second
  • Wi-Fi -- last, or off entirely during the show

If you are only running Wi-Fi and expect Companion to talk to devices over it, that is fine as long as all the devices are on the same Wi-Fi network and there is no competing wired interface on a conflicting subnet.

Remote surfaces and the Companion satellite

If you are running a Stream Deck on a separate machine -- a stage manager's laptop, a FOH operator's computer -- that machine runs Companion Satellite and connects back to the main Companion instance over the network. Satellite needs to reach Companion's IP on the satellite port (default 16622).

The common failure here is the satellite machine being on a different network segment to the Companion machine. If the main rig is on a show control LAN and the satellite is on a venue Wi-Fi, they may not be able to reach each other at all. Either put both on the same subnet, or make sure there is a routed path between them. Companion itself doesn't require anything exotic -- it just needs a TCP connection on that port.

Checking the state

If a module is showing as disconnected and you think it should be working, confirm the basics before assuming a Companion bug:

  • Can the Mac ping the device? If not, the problem is the network, not Companion.
  • Is the route for the device's subnet present? netstat -rn -f inet shows the current routing table. Look for an entry covering the device's IP range.
  • Is the adapter the route uses actually the one connected to the device? The Netif column in the routing table output shows which interface the route exits on.
  • Did Companion launch before the adapter was fully up? Restart Companion and check if the module reconnects.

Most disconnected-module problems resolve at step one. Getting Companion working reliably on a multi-adapter Mac is mostly just getting the network configuration right first.
